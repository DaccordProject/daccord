# Private chat encryption

New DM and private group messages, edits, and files are encrypted on the sending device and authenticated/decrypted on receiving devices. Space channels keep their existing message format. Both the client and server changes must be deployed together; private sends fail if the server or a participant does not support encryption. There is no plaintext fallback. Participants provision their keys when an updated client connects, so they can subsequently receive messages while offline.

Use the lock button in a private chat to compare each participant's account fingerprint through another trusted means of contacting them. The first key is trusted on first use and pinned in the platform credential vault. A key change that is not signed by the pinned key blocks sending and decryption; an account rotation signed by the previous key is followed silently (see *Removing a device*). Signing out retains encryption keys. Clearing the credential vault on every device without a backup loses access to encrypted history; the server cannot recover private keys.

Historical plaintext messages are labelled “Unencrypted history.” Reading them does not re-encrypt their server copies. A text edit replaces the message with a new encrypted revision. Legacy attachments must be re-uploaded before editing their message. Encryption covers message content and file names/types/bytes, not participant identities, device names, group names, timestamps, replies, reactions, message/file counts, or ciphertext lengths. Calls continue to use the existing voice/video transport.

## Devices

Each device has its own keys. Your **account key** (the key contacts pin and whose fingerprint they compare) is shared by your approved devices as a *keyring* that holds every account key version, so each approved device can read your whole encrypted history.

- **The first device** of an account creates the account key and becomes active. Updating from the single-identity version (v1) turns the existing identity into account version 1: the fingerprint, contacts' pins and history stay the same, and the old vault entry is kept.
- **Another device** registers as *pending*. Until it is approved, its private chats show “This device isn't approved for encrypted chats yet.” and sending is blocked with the same message. It never fails registration or retries it in a loop.
- **Approving** takes a confirmation on *both* devices. An active device is told about the pending device (gateway event `encryption.device_pending`, delivered with the `direct_messages` intent). Both devices show a 16-digit link code (four groups of four); the code covers your account key and the new device's keys, so a server that substitutes either one produces a different code. Approve on the existing device only if the codes match. The approval sends the new device a certificate and the keyring, encrypted to that device; the new device accepts it only if it matches the account key behind the code it showed, and then asks its user to confirm once more that the other device showed the same code. Only after that confirmation does it become active and reload its private history. If the codes did not match, rejecting there discards the keyring and registers the device again with a new code (remove the abandoned entry from the device list on another device). The code a pending device shows changes if the server reports a different account key; re-read it whenever the device reports it is pending. Pending devices that are not approved can be declined and expire after 24 hours. An account may have at most 20 devices.
- **Restoring from a backup** is the alternative to approval: importing a backup that contains your current account key makes the device certify itself and become active.
- **Blocked**: a device that already holds your keys never falls back to waiting for approval or to an older account key. If the server reports an account key it cannot verify from its own (for example a key that is not signed by your previous one, an older version, or a removed device reappearing), private chats on that device are blocked with “Your encryption keys don't match the server. Sending and decryption are blocked.” until the server reports keys it can verify again.

### Removing a device

Removing a lost or retired device **rotates the account key**: a new account version is created, signed by the previous one and signing it back, the remaining devices are re-certified and receive the new keyring, the removed device's session is signed out, and pending devices are discarded. The removed device cannot read messages sent afterwards, but it keeps whatever it could already read. A device cannot remove itself; remove it from another of your devices. Each device remembers the newest account version and every removed device it has seen, so a server cannot later resurrect a removed device or roll the account back. If the connection drops while removing a device, the new key is kept and the removal is completed (or discarded) when Daccord reconnects.

Contacts accept the new account version automatically because it is linked to the version they pinned by signatures in both directions; nothing needs to be re-verified, though fingerprints shown afterwards are those of the new key. A new key without a valid signature chain is treated like any other key change and blocks the chat. Older versions are trusted only when the newer, already-trusted version signed them, so a contact who first sees you after a rotation can still verify your earlier devices and messages, while keys the server invents for the past are ignored. Messages sent earlier by a removed device still verify.

## Backups

Backups require a passphrase of at least 12 characters and use PBKDF2-HMAC-SHA256 (600,000 iterations) and AES-256-GCM. They are scoped to the account and server. New backups (version 2) contain the whole keyring, so restore one made after the most recent device removal: an older backup lacks the current account key and is refused (approve the device from another one instead). Version 1 backups from earlier releases still import while the account has not been rotated.

## Protocol

AccordKit implements the shared protocol described in the server's `docs/private-chat-encryption.md`. It uses the `cryptography` package's X25519, Ed25519, HKDF-HMAC-SHA256, and AES-256-GCM implementations. Every message/revision has a new random content key, nonce, token, and ephemeral exchange key.

**v2** (`daccord-e2ee:2:`, the only format sent): messages are signed by the sending device's key, which is certified by an account key version; the signed payload also carries the sender's current account version, which receivers verify along the succession chain and which may not be older than the device's certificate. The content key is wrapped for every current participant's current account key and for each of their active devices, recipients sorted by user then key id; the server admits only that exact set and answers 409 when it is stale, after which the client refreshes discovery and retries once. Receivers verify the author's account chain from their pin through successions signed in both directions (forward from the pin, backward only via back-signatures), then the device certificate, then the device signature, and unwrap with their own device's entry or the account entry. **v1** (`daccord-e2ee:1:`) messages remain readable with any account key version in the keyring. Membership is refreshed before each send/edit; newly added members cannot decrypt previous messages and removed members receive no key for future messages. Edits preserve encrypted file keys for existing attachments.

Every device registration includes a binding signature by the device key over a hash of the session token, proving the session holds that device's key. Private keys (keyring, device key, a staged approval or rotation) and pinned public keys use the same serialized platform credential-vault boundary as session credentials, scoped by server URL and account ID. Neither Hive nor the server stores private keys. Decrypted messages and attachment descriptors stay in memory; `AccordMessage.toJson()` returns the original wire ciphertext. Image and audio previews use decrypted bytes; video playback uses a temporary app-owned file on native platforms or a browser blob URL, removed when the message widget is disposed. Saving a file explicitly writes the authenticated plaintext to the user's download destination. A process crash can leave a native temporary video file; this implementation does not promise encrypted local media storage.

REST history, individual fetches, pins, optimistic send/edit responses, and typed gateway message streams share decryption. A failed signature, context, key pin, or authenticated decryption produces an unavailable-message placeholder and exposes no file descriptors. Encrypted attachment downloads send no bearer token, reject redirects and untrusted CDN paths, and enforce size bounds. Federated DMs discover keys using the existing authenticated peer transport and use the same qualified chat/user IDs in the signed envelope on both servers. Ciphertext files are stored at the chat home and mirrored as opaque attachment metadata.

### SDK surface for the app

`PrivateChatEncryption` (`client.encryption`) exposes `setup` / `setupChanges` (`unknown`, `active`, `pending`, `approved`, `blocked`), `onDevicePending`, `onDevicesUpdate`, `initialize()` (completes normally in every state), `linkCode()` (this device), `confirmApproval()` / `rejectApproval()` (the new device's confirmation while `approved`) and `linkCodeFor(device)` (an approver; must be called before `approveDevice`, which refuses devices whose code was not computed or whose keys changed since), `listDevices()`, `approveDevice`, `declineDevice`, `removeDevices` (rotation), `checkApproval()`, and the existing `participants`, `encrypt`, `decrypt`, attachment, `fingerprint` and backup methods. `AccordClient` routes the `encryption.*` gateway events and calls `checkApproval()` on `encryption.devices_update`; a pending device's UI should also poll `checkApproval()` (e.g. every 5 s) while it shows the link code, and reload private history once `setup` becomes active. `setupChanges` re-emits `pending` whenever the link code changes (a declined or expired device registering again, a rejected approval, or a different account key), so the code must be re-read on every `pending` event.

## Residual risks

Every approved device holds the account keyring, so a stolen device that is not removed can read everything addressed to the account; removing it rotates the key so it cannot read later messages, but it keeps what it already had. A malicious server colluding with a thief could race a rotation before the owner does. Link codes are 16 decimal digits (about 53 bits) and only protect approvals where the user actually compares them. Removed devices' old signatures remain valid for history (the UI may label them later). AES-GCM is not key-committing, and clients do not reject a reused message token (the server does). A chat home could mark another server's devices as revoked in its replicas' caches. Gateway connections already open for a removed device's session are not forcibly closed by this client. This is a versioned static-key scheme, not a Double Ratchet or MLS implementation: there is no forward secrecy or post-compromise security, first-use key substitution is detectable only by comparing fingerprints, and no independent cryptographic audit is claimed.

The shared `test/fixtures/e2ee_v1.json` and `test/fixtures/e2ee_v2.json` vectors are generated by AccordKit (`E2EE_WRITE_FIXTURE=1 flutter test test/features/messaging/private_chat_interop_v2_test.dart` regenerates v2 from fixed, public test seeds) and checked by the Rust server for signature/serialization interoperability. Related message/composer and native download tests exercise the UI integration. Native media/credential-vault plugins and browser blob download behavior additionally need device/browser smoke testing.
