# Private chat encryption

New DM and private group messages, edits, and files are encrypted on the sending device and authenticated/decrypted on receiving devices. Space channels keep their existing message format. Both the client and server changes must be deployed together; private sends fail if the server or a participant does not support encryption. There is no plaintext fallback. Participants provision their keys when an updated client connects, so they can subsequently receive messages while offline.

Use the lock button in a private chat to compare each participant's identity fingerprint through another trusted means of contacting them. The first key is trusted on first use and pinned in the platform credential vault; a change blocks sending and decryption. Before using a second device, create an encrypted identity backup, save it, and keep its passphrase separately. Import it using the lock button on the second device. Backups require a passphrase of at least 12 characters and use PBKDF2-HMAC-SHA256 (600,000 iterations) and AES-256-GCM. They are scoped to the account and server. Signing out retains encryption keys. Clearing the credential vault without a backup loses access to encrypted history; the server cannot recover private keys.

Historical plaintext messages are labelled “Unencrypted history.” Reading them does not re-encrypt their server copies. A text edit replaces the message with a new encrypted revision. Legacy attachments must be re-uploaded before editing their message. Encryption covers message content and file names/types/bytes, not participant identities, group names, timestamps, replies, reactions, message/file counts, or ciphertext lengths. Calls continue to use the existing voice/video transport.

## Protocol v1

AccordKit implements the shared protocol described in the server's `docs/private-chat-encryption.md`. It uses the `cryptography` package's X25519, Ed25519, HKDF-HMAC-SHA256, and AES-256-GCM implementations. Every message/revision has a new random content key, nonce, token, and ephemeral exchange key. The content key is wrapped separately for each current participant, including the sender. Membership is refreshed before each send/edit; newly added members cannot decrypt previous messages and removed members receive no key for future messages. Edits use the current recipient list and preserve encrypted file keys for existing attachments.

Private keys and pinned public identities use the same serialized platform credential-vault boundary as session credentials, scoped by server URL and account ID. Neither Hive nor the server stores private keys. Decrypted messages and attachment descriptors stay in memory; `AccordMessage.toJson()` returns the original wire ciphertext. Image and audio previews use decrypted bytes; video playback uses a temporary app-owned file on native platforms or a browser blob URL, removed when the message widget is disposed. Saving a file explicitly writes the authenticated plaintext to the user's download destination. A process crash can leave a native temporary video file; this implementation does not promise encrypted local media storage.

REST history, individual fetches, pins, optimistic send/edit responses, and typed gateway message streams share decryption. A failed signature, context, key pin, or authenticated decryption produces an unavailable-message placeholder and exposes no file descriptors. Encrypted attachment downloads send no bearer token, reject redirects and untrusted CDN paths, and enforce size bounds. Federated DMs discover immutable identities using the existing authenticated peer transport and use the same qualified chat/user IDs in the signed envelope on both servers. Ciphertext files are stored at the chat home and mirrored as opaque attachment metadata.

This is a versioned static account-identity scheme, not a Double Ratchet or MLS implementation. It provides no forward secrecy or post-compromise recovery. The same imported identity is shared across devices, and individual devices cannot be revoked independently. First-use key substitution is detectable only by comparing fingerprints; subsequent key substitution is blocked. Private-key compromise allows decryption of retained messages encrypted for that identity. No independent cryptographic audit is claimed.

## Validation

`flutter test test/features/messaging/private_chat_encryption_test.dart` covers private send/history/edit roundtrips, channel exclusions, membership changes, signature/context tampering, missing/substituted keys, encrypted file authentication, vault failures, and backup restoration. The shared `test/fixtures/e2ee_v1.json` vector is generated by AccordKit and checked by the Rust server for signature/serialization interoperability. Related message/composer and native download tests exercise the UI integration. Native media/credential-vault plugins and browser blob download behavior additionally need device/browser smoke testing.
